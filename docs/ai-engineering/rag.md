# RAG 检索增强生成

RAG（Retrieval-Augmented Generation）：**先从知识库里检索相关资料，再把资料和问题一起交给大模型生成答案。** 它解决了大模型的三个问题：知识过时、不了解企业私有数据、容易编造。

面试讲 RAG 项目时，面试官的追问几乎都落在这几个点：切块怎么定、召回率怎么评估、怎么减少幻觉、延迟怎么优化。这篇按链路顺序整理，每一环都写出“为什么这么做”。

## 一、整体链路

RAG 分成离线和在线两部分：

```
离线（建索引）：
  文档加载 → 清洗 → 切块 → 向量化 → 写入向量库

在线（回答问题）：
  用户问题 → 问题改写 → 检索（向量 + 关键词）→ 重排
          → 拼接 Prompt → 大模型生成 → 返回答案和引用
```

一个最小可运行的版本：

```python
# 离线：建索引
chunks = split(load_documents("./docs"), chunk_size=500, overlap=50)
vectors = embed([c.text for c in chunks])
vector_db.insert(chunks, vectors)

# 在线：回答
def answer(question: str) -> str:
    q_vec = embed([question])[0]
    hits = vector_db.search(q_vec, top_k=20)        # 召回
    hits = rerank(question, hits)[:5]               # 重排
    context = "\n\n".join(f"[{i+1}] {h.text}" for i, h in enumerate(hits))
    prompt = f"""仅根据以下资料回答问题。资料中没有的信息，回答“资料中未找到”。
回答时用 [编号] 标注引用来源。

资料：
{context}

问题：{question}"""
    return llm.chat(prompt, temperature=0)
```

## 二、文档处理与切块

### 1. 为什么要切块

- 模型上下文有限，不能把整个知识库塞进去
- 检索粒度越细，返回的内容越精准，噪声越少
- 但切得太碎，单个块会丢失上下文，答案不完整

**切块大小是“精准”和“完整”之间的权衡。**

### 2. 常见切块策略

| 策略 | 做法 | 适合 |
| --- | --- | --- |
| 固定长度 | 每 N 个 token 切一刀，相邻块重叠一部分 | 结构松散的纯文本，简单好用 |
| 递归切分 | 优先按段落切，太长再按句子切，再按字符切 | 通用场景，LangChain 默认方式 |
| 按文档结构 | 按标题层级、章节、表格、代码块切 | 制度文档、产品手册、Markdown |
| 语义切分 | 相邻句子 Embedding 相似度骤降处切开 | 主题频繁切换的长文 |
| 父子块（Small-to-Big） | 用小块检索，命中后返回所在的大块 | 既要检索精准又要上下文完整 |

### 3. 切块参数怎么定（追问高频）

不要回答“我用了 500”，要回答**怎么得出的**：

1. 先根据文档类型给初始值：问答类、条款类文档 200～500 token；叙述性长文 500～1000 token
2. 重叠一般取块长的 10%～20%，防止一句话被切断在两个块里
3. **用评估集做对比实验**：准备几十到上百个真实问题和标准答案，分别用不同块大小建索引，比较召回率和最终回答准确率，选效果最好的
4. 表格、代码这类不能拆的内容单独处理，保持完整

### 4. 数据清洗容易被忽略

- 去掉页眉页脚、目录、重复的免责声明
- PDF 的表格、多栏排版要专门解析，否则顺序会乱
- 给每个块保留**元数据**：来源文件、标题路径、更新时间、所属部门。检索时可以按元数据过滤，回答时可以给出引用

## 三、检索

### 1. 向量检索

问题和文档块都转成向量，找最相似的 top_k 个。

- **向量数据库**：Milvus、Elasticsearch（支持向量）、pgvector、FAISS（库，不是数据库）
- **近似最近邻（ANN）索引**：数据量大时不可能逐个比较，用 HNSW（图索引，速度和召回都好，内存占用大）、IVF（先聚类再在相近的簇里找）等

### 2. 混合检索

纯向量检索的短板：**对专有名词、编号、型号不敏感**。比如用户问“套餐 5G-A 畅享 199”，向量检索可能召回一堆讲其他套餐的内容。

解决：**向量检索 + 关键词检索（BM25）一起召回，再合并排序**（常用 RRF 倒数排名融合）。

### 3. 问题改写

用户的原始问题往往不适合直接检索：

- **指代补全**：多轮对话里“那它多少钱？”要改写成“XX 套餐多少钱？”
- **问题扩展**：生成几个同义问法分别检索（Multi-Query）
- **HyDE**：先让模型生成一个“假设答案”，用假设答案去检索，因为答案和文档的表述更接近

### 4. 重排（Rerank）

召回阶段追求“别漏”，取 20～50 条；重排阶段追求“排准”，用 Cross-Encoder 重排模型（如 bge-reranker）精排后取前 3～5 条交给大模型。

原因见 [大模型基础 - 双塔与交叉编码](/ai-engineering/llm-basics#_4-双塔与交叉编码)：重排模型精度高但慢，只适合处理少量候选。

## 四、评估：怎么知道 RAG 好不好

### 1. 先建评估集

评估的前提是有标注数据：**真实问题 + 标准答案 + 应该被检索到的文档块**。来源可以是历史客服记录、业务人员整理，也可以用大模型从文档生成问题后人工校对。

### 2. 检索阶段的指标

| 指标 | 含义 |
| --- | --- |
| Recall@k（召回率） | 应该召回的相关块，有多少出现在前 k 个结果里 |
| Hit Rate@k（命中率） | 前 k 个结果里至少有一个相关块的问题占比 |
| MRR | 第一个相关块排名的倒数的平均值，衡量“排得靠不靠前” |
| nDCG | 考虑多个相关块及其位置的综合排序质量 |

### 3. 生成阶段的指标

- **忠实度（Faithfulness）**：答案是否都能在检索资料中找到依据，衡量幻觉
- **答案相关性**：答案是否回答了问题
- **答案正确性**：和标准答案对比

常用工具：RAGAS 框架，用大模型当裁判（LLM-as-Judge）自动打分，再抽样人工复核。

### 4. 面试回答模板

> 我们准备了 X 条真实业务问题作为评估集，每条标注了标准答案和相关文档。检索阶段看 Recall@5 和 MRR，生成阶段用 RAGAS 看忠实度和答案正确性。优化前 Recall@5 是 A%，加了混合检索和重排之后提升到 B%。

（把 X、A、B 换成你项目里的真实数字。没有做过评估就如实说“当时用人工抽检”，并说出现在会怎么改进。）

## 五、减少幻觉

幻觉的来源有两类，对应的手段也不同：

**检索没找到对的资料**（多数幻觉的真正原因）：

- 提升召回：混合检索、问题改写、调整切块
- 设置相关度阈值：重排分数太低就不给模型资料，直接回答“未找到”

**模型没老实用资料**：

- Prompt 明确约束：“仅根据资料回答，资料中没有就说不知道”
- 要求标注引用来源，并在前端展示原文，用户可以核对
- `temperature` 调低（0～0.3）
- 生成后校验：再用一次模型或规则检查答案中的关键信息（数字、日期、名称）是否在资料里出现过
- 关键场景（资费、合同条款）采用“检索结果原文展示 + 模型总结”的方式，不让模型自由改写数字

## 六、性能优化

RAG 的延迟 = 问题改写 + 向量化 + 检索 + 重排 + 大模型生成，大头在生成。

- **流式输出**：首个字尽快返回，用户感知延迟大幅下降
- **并行**：向量检索和关键词检索同时进行
- **缓存**：高频问题做语义缓存，相似问题直接返回历史答案；Embedding 结果也可以缓存
- **控制上下文长度**：重排后只保留最相关的几块，输入越短生成越快、成本越低
- 模型服务本身的优化见 [大模型服务部署与性能优化](/ai-engineering/model-serving)

## 七、进阶方向

- **GraphRAG**：从文档中抽取实体和关系构建知识图谱，适合需要跨文档推理的问题
- **Agentic RAG**：让 Agent 自己决定要不要检索、检索几次、换什么关键词（见 [Agent 智能体开发](/ai-engineering/agent)）
- **多模态 RAG**：检索图片、表格、扫描件

## 八、高频追问清单

1. 切块大小怎么定的？有没有做对比？
2. 向量检索召回不准怎么办？
3. 召回率怎么评估？评估集从哪来？
4. 怎么减少幻觉？
5. 知识库更新了怎么办？（增量更新：按文档 ID 删除旧块、写入新块，元数据记录版本和更新时间）
6. 多轮对话怎么处理？（问题改写，补全指代）
7. 文档有权限怎么办？（块的元数据记录权限，检索时按用户身份过滤）
8. 延迟多少？怎么优化的？
