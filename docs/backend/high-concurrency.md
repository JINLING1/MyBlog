# 高并发系统设计

岗位描述里有一条“解决高并发、大数据量场景下的技术挑战”。运营商的业务天然是高并发的：几千万用户同时查话费、抢购活动、营业厅系统。这篇按“衡量 → 扩展 → 缓存 → 异步 → 保护 → 数据库”的顺序整理。

## 一、先说清楚指标

| 指标 | 含义 |
| --- | --- |
| QPS / TPS | 每秒查询数 / 每秒事务数 |
| RT（响应时间） | 关注平均值，更要关注 P95、P99 |
| 并发数 | 同时处理的请求数，≈ QPS × 平均响应时间 |
| 可用性 | 99.99% 意味着一年停机不超过约 53 分钟 |

> 面试回答高并发问题时，先问清楚或者假设出量级（比如峰值 QPS 一万），方案才有依据。

## 二、整体思路

```
用户 → CDN（静态资源）→ 负载均衡（Nginx）→ 网关（鉴权、限流）
     → 应用服务集群（无状态，水平扩展）
     → 缓存（本地缓存 + Redis）
     → 消息队列（异步、削峰）
     → 数据库（读写分离、分库分表）
```

核心手段可以概括为：**能缓存的缓存，能异步的异步，能拆分的拆分，扛不住的限流降级。**

## 三、水平扩展与负载均衡

### 1. 服务无状态

扩展的前提是服务**无状态**：会话信息不存在单台机器的内存里，而是放在 Redis 或用 JWT。这样任何一台机器都能处理任何请求，加机器就能提升能力。

### 2. 负载均衡算法

| 算法 | 特点 |
| --- | --- |
| 轮询 | 依次分配，简单 |
| 加权轮询 | 性能好的机器分得多 |
| 最少连接 | 分给当前连接最少的机器，适合请求耗时差异大的场景（如大模型推理） |
| IP 哈希 / 一致性哈希 | 同一用户固定到同一台机器，适合有本地缓存的场景 |

## 四、缓存

缓存是提升读性能最有效的手段，可以分层：

| 层 | 例子 |
| --- | --- |
| 浏览器缓存 | HTTP 缓存头 `Cache-Control` |
| CDN | 图片、JS、CSS 等静态资源 |
| 本地缓存 | Caffeine、Guava Cache，最快但各实例数据可能不一致 |
| 分布式缓存 | Redis |

缓存的问题和一致性见 [Redis 与缓存](/backend/redis)。

## 五、异步与消息队列

### 1. 三大作用

- **解耦**：下单后要发短信、加积分、开发票，订单服务只发一条消息，其他服务各自订阅
- **异步**：非核心步骤不在主流程里同步等待，响应更快
- **削峰**：秒杀等瞬时流量先进入队列，后端按自己的处理能力消费，保护数据库

常用：Kafka（吞吐量大，日志和大数据场景）、RocketMQ（业务消息，支持事务消息和延时消息）、RabbitMQ。

### 2. 引入消息队列带来的问题

| 问题 | 解决 |
| --- | --- |
| 消息丢失 | 生产者确认、消息持久化、消费者处理完再提交确认 |
| 重复消费 | 消费者做**幂等**处理（见第八节） |
| 消息积压 | 增加消费者、批量消费、排查消费慢的原因 |
| 顺序性 | 需要有序的消息发到同一个分区 / 队列 |

## 六、限流、熔断与降级

系统总有上限，超过上限时要“有序地拒绝”，而不是整体崩溃。

### 1. 限流算法

| 算法 | 原理 | 特点 |
| --- | --- | --- |
| 固定窗口 | 每个时间窗口计数，超过就拒绝 | 简单，窗口边界可能出现两倍流量 |
| 滑动窗口 | 把窗口切成更小的格子滑动统计 | 更平滑 |
| 漏桶 | 请求进桶，以固定速率流出 | 输出速率恒定，不能应对突发 |
| 令牌桶 | 以固定速率往桶里放令牌，请求拿到令牌才处理 | 允许一定突发流量，**最常用** |

实现：单机用 Guava `RateLimiter`；分布式用 Redis + Lua；网关层用 Nginx、Sentinel、Spring Cloud Gateway。

### 2. 熔断

下游服务出现大量错误或超时时，**暂时停止调用它**，直接返回失败或默认值，避免自己的线程被拖住，导致故障在整个调用链上扩散（雪崩）。过一段时间后放少量请求试探，恢复正常再关闭熔断。

```
关闭（正常调用）→ 错误率超过阈值 → 打开（直接失败）
→ 等待一段时间 → 半开（放少量请求试探）→ 成功则关闭，失败则重新打开
```

### 3. 降级

资源紧张时**主动关闭非核心功能**，保证核心功能可用。比如大促期间关闭推荐、评论，只保证下单和支付；大模型服务繁忙时切换到小模型或返回预设回复。

### 4. 超时与重试

- 所有远程调用都要设置超时
- 重试只针对可重试的错误，次数有限，配合**指数退避**
- 重试的接口必须幂等

## 七、数据库扩展

数据库通常是最后的瓶颈，按顺序考虑：

1. **SQL 和索引优化**（见 [SQL](/it-basics/sql)）
2. **连接池**：合理设置连接数，避免频繁建立连接
3. **缓存**：挡住大部分读请求
4. **读写分离**：主库写、从库读。注意主从延迟，刚写完马上读要走主库
5. **分库分表**：
   - 垂直拆分：按业务拆成不同的库（用户库、订单库）
   - 水平拆分：同一张表按用户 ID 哈希等规则拆到多个库表
   - 代价：跨库查询、分布式事务、全局唯一 ID（雪花算法）都变复杂，是最后的手段
6. **换存储**：海量写入的日志、话单用 HBase、ClickHouse 等

## 八、幂等

**同一个请求执行一次和执行多次，结果相同。** 网络超时重试、消息重复消费、用户重复点击都会产生重复请求。

常用做法：

- **唯一索引**：订单号建唯一索引，重复插入直接失败
- **Token 机制**：提交前先获取一个 Token，提交时校验并删除，第二次提交 Token 已不存在
- **状态机**：`UPDATE order SET status = '已支付' WHERE id = ? AND status = '待支付'`，只有从特定状态才能变更
- **去重表 / Redis 记录**：记录已处理的请求 ID

## 九、典型场景：秒杀

综合运用上面的手段：

1. **前端**：按钮防重复点击，静态页面放 CDN
2. **网关**：限流，超出的请求直接返回“活动太火爆”
3. **库存预扣**：库存提前加载到 Redis，用 Lua 脚本原子地判断并扣减
4. **异步下单**：扣减成功后发消息，订单服务异步创建订单，前端轮询结果
5. **防超卖**：数据库最终扣减时 `UPDATE stock SET count = count - 1 WHERE id = ? AND count > 0`
6. **防刷**：同一用户限购，验证码、风控

## 十、大模型服务的特殊之处

大模型服务的并发瓶颈在 GPU，单个请求耗时长、资源重，所以：

- 比起“扛住”，更强调**排队、限流和优先级**
- 推理侧用连续批处理提升吞吐
- 缓存的价值更大（一次推理的成本远高于一次数据库查询）
- 用流式输出降低感知延迟

详见 [大模型服务部署与性能优化](/ai-engineering/model-serving)。

## 十一、高频面试题

1. **如果让你设计一个高并发系统，你会从哪些方面考虑？** 按第二节的链路逐层回答：扩展、缓存、异步、限流熔断、数据库。
2. **限流算法有哪些？令牌桶和漏桶的区别？** 令牌桶允许突发，漏桶输出恒定。
3. **熔断和降级的区别？** 熔断是对下游故障的被动保护；降级是主动关闭非核心功能保核心。
4. **消息队列怎么保证消息不丢失、不重复？** 确认机制保证不丢；消费端幂等处理重复。
5. **怎么保证接口幂等？** 唯一索引、Token、状态机、去重表。
6. **秒杀系统怎么设计？** 见第九节。
