# Redis 与缓存

Redis 是基于内存的键值数据库，几乎所有后端系统都用它做缓存。面试的问题集中在：为什么快、数据类型怎么用、缓存出问题怎么办、缓存和数据库怎么保持一致。

## 一、数据类型与应用场景

| 类型 | 结构 | 典型场景 |
| --- | --- | --- |
| String | 字符串、数字 | 缓存对象（JSON）、计数器、分布式锁、验证码 |
| Hash | 字段 → 值 | 存储对象的多个字段（用户信息），可单独修改某个字段 |
| List | 有序列表 | 消息队列（简单场景）、最新动态列表 |
| Set | 无序去重集合 | 标签、共同好友（交集）、抽奖 |
| ZSet | 带分数的有序集合 | 排行榜、延时队列（分数存时间戳） |

特殊类型：

- **Bitmap**：按位存储，用于签到、在线状态，一亿用户的签到一天只占约 12MB
- **HyperLogLog**：基数统计，用固定的约 12KB 估算 UV，有约 0.81% 误差
- **Stream**：Redis 5.0 起的消息队列，支持消费者组和消息确认

```bash
SET user:1001 '{"name":"张三"}' EX 3600     # 缓存，1 小时过期
INCR article:42:views                       # 阅读数加一
ZADD rank 98 "user:1001"                    # 排行榜加分
ZREVRANGE rank 0 9 WITHSCORES               # 前十名
```

## 二、Redis 为什么快

1. **纯内存操作**，读写在微秒级
2. **单线程执行命令**，没有锁竞争和线程切换的开销
3. **I/O 多路复用**（epoll），一个线程就能处理大量连接（见 [操作系统 - I/O 模型](/it-basics/os#五、i-o-模型)）
4. **高效的数据结构**：SDS、跳表、压缩列表等

> 补充：Redis 6.0 引入了多线程 I/O，但**多线程只用于网络读写**，命令执行仍然是单线程的，所以依然不用考虑命令之间的并发问题。

**单线程的代价**：一个慢命令会阻塞所有请求。所以要避免 `KEYS *`（用 `SCAN`）、避免大 Key（一个 Hash 有上百万字段、一个 String 有几十 MB）。

## 三、持久化

| | RDB | AOF |
| --- | --- | --- |
| 方式 | 定时生成内存快照 | 记录每条写命令 |
| 恢复速度 | 快 | 慢（要重放命令） |
| 数据丢失 | 可能丢失最后一次快照之后的数据 | 取决于刷盘策略，`everysec` 最多丢 1 秒 |
| 文件大小 | 小 | 大（会定期重写压缩） |

实际一般开启**混合持久化**（Redis 4.0+）：AOF 重写时先写入 RDB 格式的快照，再追加之后的命令，兼顾恢复速度和数据安全。

## 四、过期与内存淘汰

### 1. 过期删除策略

- **惰性删除**：访问某个 Key 时才检查是否过期
- **定期删除**：每隔一段时间随机抽查一部分设置了过期时间的 Key

两者结合，既不会占用太多 CPU，也不会让过期 Key 长期留在内存里。

### 2. 内存淘汰策略

内存达到 `maxmemory` 上限时：

| 策略 | 行为 |
| --- | --- |
| noeviction（默认） | 拒绝写入 |
| allkeys-lru | 所有 Key 中淘汰最近最少使用的，**做缓存时最常用** |
| volatile-lru | 只在设置了过期时间的 Key 中淘汰 |
| allkeys-lfu | 淘汰使用频率最低的 |
| volatile-ttl | 淘汰最快过期的 |

## 五、缓存的三大问题

### 1. 缓存穿透

**查询一个根本不存在的数据**，缓存里没有，每次都打到数据库。常见于恶意攻击（用不存在的 ID 大量请求）。

解决：

- **缓存空值**：数据库查不到也缓存一个空值，设置较短的过期时间
- **布隆过滤器**：把所有存在的 ID 放进布隆过滤器，请求先过一遍，判断不存在就直接返回
- 参数校验：明显非法的 ID 直接拦截

> 布隆过滤器的特点：说“不存在”就一定不存在，说“存在”可能误判。

### 2. 缓存击穿

**一个热点 Key 过期的瞬间**，大量请求同时打到数据库。

解决：

- **互斥锁**：只让一个请求去查数据库并重建缓存，其他请求等待或返回旧值
- **逻辑过期**：不设置真正的过期时间，在值里存一个过期时间字段，发现过期后异步更新，期间先返回旧值
- 热点数据不过期，或者提前续期

### 3. 缓存雪崩

**大量 Key 同时过期，或 Redis 宕机**，请求全部打到数据库。

解决：

- **过期时间加随机值**，让 Key 分散过期
- **Redis 高可用**：主从 + 哨兵，或者集群
- **限流降级**：数据库前加限流，超出部分返回默认值
- **多级缓存**：本地缓存（Caffeine）+ Redis

### 记忆方法

| 问题 | 关键词 | 核心解法 |
| --- | --- | --- |
| 穿透 | 数据不存在 | 布隆过滤器、缓存空值 |
| 击穿 | 一个热点 Key 过期 | 互斥锁、逻辑过期 |
| 雪崩 | 大量 Key 过期 / 宕机 | 随机过期时间、高可用 |

## 六、缓存与数据库的一致性

### 1. 推荐方案：Cache Aside（旁路缓存）

- **读**：先读缓存，没有就读数据库，再写入缓存
- **写**：**先更新数据库，再删除缓存**

### 2. 为什么是“删除”缓存而不是“更新”缓存

- 更新缓存在并发时容易写入旧值（两个写请求的执行顺序交错）
- 很多缓存值是计算出来的，每次写都更新很浪费，可能根本没人读
- 删除后下次读取时再加载，是“懒加载”

### 3. 为什么是“先更新数据库，再删缓存”

如果先删缓存再更新数据库：删除之后、更新之前，另一个读请求进来发现缓存为空，读到**旧数据**并写回缓存，缓存里就一直是旧值了。

先更新数据库再删缓存也有极小概率不一致，但需要“读请求在更新前读到旧值，又在删除之后才写回缓存”，而写缓存通常远快于写数据库，所以概率很低。

### 4. 进一步保证

- **延迟双删**：更新数据库 → 删缓存 → 延迟几百毫秒再删一次
- **删除失败重试**：删除缓存失败时放入消息队列重试
- **订阅 binlog**：用 Canal 监听数据库变更，异步删除缓存，业务代码不用关心
- 所有缓存都设置过期时间，作为最后兜底

> 缓存和数据库无法做到强一致，只能做到最终一致。对一致性要求极高的数据（账户余额）不应该依赖缓存读取。

## 七、分布式锁

多个服务实例要互斥执行某段逻辑（防止重复下单、定时任务只执行一次）时使用。

### 1. 基本实现

```bash
# 加锁：不存在才设置，30 秒后自动过期（防止服务宕机后锁永远不释放）
SET lock:order:1001 <唯一ID> NX PX 30000
```

```lua
-- 解锁：用 Lua 脚本保证“判断是不是自己的锁”和“删除”是原子的
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

### 2. 关键点

- **必须设置过期时间**，否则加锁的服务宕机后锁永远不释放
- **值用唯一 ID**，解锁时校验，防止删除别人的锁（自己的锁已过期、被别人拿到了）
- **业务执行时间超过过期时间怎么办**：用“看门狗”自动续期。Java 中直接用 **Redisson**，它实现了可重入、自动续期、公平锁等功能

## 八、高可用

| 方案 | 作用 |
| --- | --- |
| 主从复制 | 主节点写，从节点读，数据复制到从节点 |
| 哨兵（Sentinel） | 监控主节点，宕机时自动把从节点升为主节点 |
| 集群（Cluster） | 数据分片到多个主节点（16384 个哈希槽），解决单机容量和写入瓶颈 |

## 九、在 AI 应用中的用法

- **会话记忆**：多轮对话的历史消息存在 Redis，设置过期时间
- **结果缓存与语义缓存**：相同或相似的问题直接返回（见 [模型服务部署](/ai-engineering/model-serving#四、缓存)）
- **限流**：按用户统计 QPS 和 token 用量
- **任务状态**：异步任务（文档解析、批量生成）的进度
- **向量检索**：Redis Stack 也支持向量索引，适合数据量不大的场景
