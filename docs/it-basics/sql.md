# SQL

数据库是后端面试的必考项。这篇从“关系型和非关系型的区别”讲起，再到存储模式、索引、事务和 SQL 优化。MySQL 是讨论的默认对象。

## 一、关系型与非关系型数据库

### 1. 区别

| | 关系型（SQL） | 非关系型（NoSQL） |
| --- | --- | --- |
| 数据模型 | 二维表，行和列，有固定的表结构 | 键值、文档、列族、图等，结构灵活 |
| 查询 | SQL，支持复杂的关联查询 | 各自的 API，关联查询弱 |
| 事务 | 完整支持 ACID | 多数只支持单条记录或弱事务 |
| 扩展 | 以垂直扩展为主，水平扩展（分库分表）复杂 | 天然支持水平扩展 |
| 一致性 | 强一致 | 多为最终一致（BASE） |
| 代表 | MySQL、PostgreSQL、Oracle | Redis、MongoDB、HBase、Neo4j |

### 2. NoSQL 的四种类型

| 类型 | 代表 | 适合 |
| --- | --- | --- |
| 键值 | Redis | 缓存、会话、计数器、排行榜 |
| 文档 | MongoDB | 结构多变的数据：日志、内容、配置 |
| 列族 | HBase、Cassandra | 海量数据写入：话单、监控数据、用户行为 |
| 图 | Neo4j | 关系网络：社交关系、知识图谱、风控 |

另外，**向量数据库**（Milvus 等）是 AI 应用里新兴的一类，专门存储和检索向量，见 [RAG](/ai-engineering/rag)。

### 3. 怎么选

> 不是二选一，而是组合使用。核心业务数据（用户、订单、账务）要求强一致和事务，用关系型数据库；高频读取的热点数据用 Redis 缓存；海量日志和行为数据用 HBase 或 Elasticsearch；AI 检索用向量数据库。

### 4. ACID、CAP 与 BASE

- **ACID**（关系型事务的四个特性）：原子性、一致性、隔离性、持久性
- **CAP**：分布式系统中，一致性（C）、可用性（A）、分区容错性（P）最多同时满足两个。网络分区不可避免，所以实际是在 C 和 A 之间取舍
- **BASE**：基本可用、软状态、最终一致。是 NoSQL 和分布式系统放弃强一致、换取可用性的思路

## 二、存储模式

### 1. 行存储与列存储

| | 行存储 | 列存储 |
| --- | --- | --- |
| 存放方式 | 一行的所有字段连续存放 | 同一列的数据连续存放 |
| 擅长 | 按行读写、频繁增删改 | 对少数列做统计聚合 |
| 压缩 | 一般 | 好（同一列数据类型相同、重复多） |
| 场景 | OLTP（在线交易） | OLAP（数据分析） |
| 代表 | MySQL InnoDB、PostgreSQL | ClickHouse、Hive（ORC/Parquet）、Doris |

例子：查“某用户的全部信息”行存储快；统计“全省上个月平均流量”只需读一列，列存储快得多。

### 2. MySQL 存储引擎

| | InnoDB（默认） | MyISAM |
| --- | --- | --- |
| 事务 | 支持 | 不支持 |
| 锁 | 行锁 | 表锁 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 支持（redo log） | 不支持 |

现在基本都用 InnoDB。

## 三、索引

### 1. 为什么用 B+ 树

索引的目的是减少磁盘 I/O。B+ 树的特点：

- **矮胖**：每个节点存很多键，三四层就能存千万级数据，查询只需三四次磁盘 I/O
- **数据只存在叶子节点**，非叶子节点能放更多键
- **叶子节点用链表相连**，范围查询（`BETWEEN`、`>`）很高效

对比：哈希索引等值查询快但不支持范围查询和排序；二叉树太高；B 树的非叶子节点也存数据，同样大小的节点能放的键更少，而且范围查询要回到上层节点。

### 2. 聚簇索引与二级索引

- **聚簇索引**（主键索引）：叶子节点存的是**整行数据**。一张表只有一个
- **二级索引**（普通索引）：叶子节点存的是**主键值**
- **回表**：通过二级索引查到主键，再到聚簇索引里查整行
- **覆盖索引**：查询的字段都在索引里，不需要回表。比如对 `(name, age)` 建了联合索引，`SELECT name, age FROM user WHERE name = ?` 就不用回表

### 3. 联合索引与最左前缀

对 `(a, b, c)` 建联合索引，相当于建了 `(a)`、`(a, b)`、`(a, b, c)` 三个索引。查询条件要**从最左边的列开始连续使用**才能用上。

- `WHERE a = 1 AND b = 2` ✅
- `WHERE b = 2` ❌ 没有 a
- `WHERE a = 1 AND c = 3` 只有 a 用上了索引
- `WHERE a > 1 AND b = 2` a 是范围查询，b 用不上

### 4. 索引失效的常见情况

- 对索引列使用函数或计算：`WHERE YEAR(create_time) = 2026`
- 隐式类型转换：手机号是字符串，写成 `WHERE phone = 13800000000`
- 左模糊匹配：`LIKE '%宽带'`
- `OR` 两边有一列没有索引
- 不满足最左前缀
- 优化器判断全表扫描更快（比如区分度很低的字段）

### 5. 建索引的原则

- 给 `WHERE`、`JOIN`、`ORDER BY` 常用的列建索引
- 区分度高的列放在联合索引前面
- 不是越多越好：索引占空间，还会拖慢写入
- 尽量用覆盖索引，避免 `SELECT *`

## 四、事务

### 1. 并发问题

| 问题 | 含义 |
| --- | --- |
| 脏读 | 读到了别的事务还没提交的数据 |
| 不可重复读 | 同一事务里两次读同一行，结果不同（被别人修改了） |
| 幻读 | 同一事务里两次范围查询，行数不同（被别人插入了） |

### 2. 四种隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交 | 不会 | 可能 | 可能 |
| 可重复读（MySQL 默认） | 不会 | 不会 | 大部分情况不会 |
| 串行化 | 不会 | 不会 | 不会 |

MySQL 在可重复读级别下，普通查询靠 MVCC 快照避免幻读，加锁查询靠**间隙锁**避免幻读。

### 3. MVCC（多版本并发控制）

让读和写互不阻塞：

- 每行数据有隐藏字段记录最后修改的事务 ID，旧版本通过 **undo log** 串成版本链
- 事务读取时生成一个 **Read View**，根据它判断版本链中哪个版本对自己可见
- 读已提交：每次查询都生成新的 Read View
- 可重复读：事务中第一次查询时生成，之后一直复用，所以多次读结果一致

### 4. 三大日志

- **undo log**：记录修改前的数据，用于回滚和 MVCC
- **redo log**：记录修改后的数据，用于崩溃恢复，保证持久性
- **binlog**：MySQL 服务层的日志，用于主从复制和数据恢复

## 五、SQL 编写与优化

### 1. 执行顺序

```sql
SELECT region, COUNT(*) AS cnt        -- 5
FROM user                             -- 1
WHERE status = 1                      -- 2
GROUP BY region                       -- 3
HAVING COUNT(*) > 100                 -- 4
ORDER BY cnt DESC                     -- 6
LIMIT 10;                             -- 7
```

所以 `WHERE` 里不能用 `SELECT` 中定义的别名，也不能用聚合函数；对分组结果过滤要用 `HAVING`。

### 2. 常考写法

```sql
-- 每个地市流量使用量前三的用户（窗口函数，MySQL 8.0+）
SELECT *
FROM (
  SELECT city, user_id, data_gb,
         ROW_NUMBER() OVER (PARTITION BY city ORDER BY data_gb DESC) AS rn
  FROM usage_monthly
) t
WHERE rn <= 3;

-- LEFT JOIN：查出没有任何订单的用户
SELECT u.id, u.name
FROM user u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```

### 3. 慢查询优化步骤

1. 开启慢查询日志，找到慢 SQL
2. 用 `EXPLAIN` 看执行计划，重点看：
   - `type`：从好到差 `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`（全表扫描）
   - `key`：实际用到的索引
   - `rows`：预估扫描行数
   - `Extra`：出现 `Using filesort`、`Using temporary` 要警惕，`Using index` 表示覆盖索引
3. 针对性优化：加或调整索引、改写 SQL、避免 `SELECT *`
4. 深分页优化：`LIMIT 1000000, 10` 会扫描一百万行，改为 `WHERE id > 上一页最大 id LIMIT 10`

### 4. 数据量继续增长怎么办

1. 加缓存（Redis），减少数据库读压力
2. 读写分离：主库写、从库读
3. 分库分表：按用户 ID 等字段水平拆分。代价是跨库查询、分布式事务变复杂，是最后的手段

## 六、高频面试题

1. **关系型和非关系型数据库的区别？各自适合什么场景？** 见第一节。
2. **行存储和列存储的区别？** 见第二节。
3. **为什么用 B+ 树不用 B 树或哈希？** 矮胖、I/O 少；叶子节点链表适合范围查询；哈希不支持范围和排序。
4. **什么是回表和覆盖索引？** 见第三节。
5. **索引什么情况下会失效？** 函数计算、隐式类型转换、左模糊、不满足最左前缀等。
6. **事务隔离级别有哪些？MySQL 默认哪个？** 四种，默认可重复读。
7. **MVCC 的原理？** 版本链 + Read View。
8. **一条 SQL 很慢怎么排查？** 慢查询日志 → EXPLAIN → 优化索引或改写。
